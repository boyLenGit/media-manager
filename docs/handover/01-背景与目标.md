# 01 · 背景与目标

## 1. 为什么造这个轮子

用户是一个有大量本地视频资源的群晖 NAS 用户。已有的方案都有各自不爽的点:

| 现有方案 | 痛点 |
|---|---|
| **群晖 Video Station** | 只认"电影/电视剧"这种规整命名,对乱七八糟命名的资源(B 站下载、动漫生肉、字幕组压制版等)几乎不可用;分类维度死板 |
| **Jellyfin / Plex** | 定位是"媒体服务器 + 刮削 + 转码",对**非影视类**(教程、素材、ASMR、个人收藏)支持差;强依赖 TMDB 式元数据匹配,匹配不上就一团糟;界面重 |
| **纯文件管理器 / File Station** | 只能看文件树,没有标签/作者/观看状态/评分/去重这些"管理"能力 |
| **Ban 掉的下载器** | qB/BitComet 各有 WebUI,但和"资源库"是割裂的,下完的东西还得手动整理 |

**核心诉求**:一个**以"管理"为中心、不挑资源类型、命名容错强**的私人媒体库,能把「扫描 → 解析 → 打标签 → 播放 → 下载」串成一条自动化链路。

---

## 2. 产品定位

一句话:**私人 NAS 上的媒体资源"管理台 / 主入口"**。

关键定位选择:

- **管理 > 播放**:核心价值是把杂乱资源组织成可检索、可分类、可去重的库。播放是能力之一,不是全部。
- **不挑资源类型**:影视、动漫、教程、素材、任意视频都能管。不强制影视元数据匹配。
- **命名容错**:用可插拔的解析器(parser pipeline)处理各种奇葩文件名,而不是要求用户先规整命名。
- **Jellyfin 是"下游"不是"对手"**:Media Manager 是入口,可以把某个资源"跳转到 Jellyfin 播放"。两者协作。
- **轻量**:SQLite 单文件库、单容器部署、不需要 Redis/PG。适合 NAS 这种资源受限环境。

---

## 3. 目标用户 & 场景

- **主用户**:技术型 NAS 玩家(会 SSH、会 docker、懂 BT)
- **典型场景**:
  1. NAS 上堆了几百上千个视频,命名乱,想统一管理
  2. 想给视频打自定义标签(不只是"电影/剧集",而是"知识点"、"待看"、"某 UP 主"等任意维度)
  3. 想在网页直接播放(或一键唤起本地 IINA/VLC)
  4. 想搜索 + 下载新资源,下完自动进库
  5. 想标记视频的时间点(书签,类似 B 站"硬币时刻")
  6. 想找出库里的重复资源清理掉

---

## 4. 设计原则

1. **薄 API 层,业务下沉 service**:`api/` 只做参数校验 + 调用,逻辑在 `services/`。
2. **适配器模式做扩展点**:解析器、搜索源、下载器、播放目标都是 provider,加新的不动核心。
3. **SQL migration 手写,不引入 Alembic**:NAS 场景,轻量优先。
4. **数据安全第一**:所有"删除""清空"都要二次确认(危险操作还要密码),写审计日志;真实磁盘文件默认不动。
5. **中文优先**:团队是中文的,注释、commit、UI 都中文(i18n 是 backlog)。

---

## 5. 非目标(明确不做的)

写清楚"不做什么"和"做什么"一样重要:

- **不做转码服务器**:不实时转码(GPU 转码是探索性 backlog,非核心)。播不了的格式引导用户用本地播放器。
- **不做媒体刮削平台**:海报/元数据自动抓取(TMDB/豆瓣)是 backlog,但不是核心定位,不会做成 Plex 那样重。
- **不做 BT 客户端**:下载委托给 qBittorrent,自己不实现 BT 协议。
- **不上重型基础设施**:不引入 Redis / PostgreSQL / Kafka / 微服务。SQLite + 单进程够用。
- **不做多租户 SaaS**:是**私人**部署,不是公网多用户服务(虽然有基础的多用户账号体系)。
- **不追求测试覆盖率**:纯逻辑模块可以加 pytest,但不为覆盖率而覆盖率。
